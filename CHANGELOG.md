# Changelog

What changed in CUI, newest first. Every component mentioned here runs live in the docs.

## Unreleased

### Added

- **Terminal screen: ligatures, keeping the grid (opt in): `cui_vt_look.ligatures`, `cui_vt_look.font_features`, `cui_font_ligatures`; the CMake option `CUI_VT_LIGATURES`.** With `.ligatures` a font that has programming ligatures (Cascadia Code, Fira Code, JetBrains Mono: its calt, liga, clig, rlig) draws `=>` `!=` `->` `===` as one sign in the cells of their characters: no cell ever moves, and a ligature breaks where the style changes, at the cursor and at the edges of the selection. Runs are cut at spaces and at the characters no lookup starts with, shaped once and kept (1024 pieces, 4 ways), so a flood of code costs what it did. `.font_features` turns more of the font's OpenType features on (`ss01,zero`) or off (`-calt`). `cui_font_ligatures(ui, font)` says whether a font has any (for a setting's note). A font with none (Geist Mono, Cascadia Mono, Consolas) draws exactly as before. Needs the shaper: `CUI_VT_LIGATURES` builds its GSUB alone (about 10 KB at -Os), or `CUI_TEXT_SHAPING`. The shaper gains `cui__shape_plan` / `cui__shape_gsub` (the lookups of a feature set in lookup-list order, each with a digest of the glyphs that can start it) and checks a format 3 context rule's first input before its backtrack, so shaping is about 20 times faster for a font with many contextual lookups. Default: off, as before.
- **Terminal screen: save a screen and load it again (opt in, for restoring terminals after a restart): `cui_vt_save`, `cui_vt_load`, `cui_vt_saved`, `cui_vt_saved_free`, `CUI_VT_SAVE_VERSION`.** `cui_vt_save` appends the main screen's rows and the newest scrollback rows (at most `max_lines` together, also while the alternate screen is shown) to a growing buffer, as a versioned header and a terminal byte stream that uses only SGR, CUF, ECH, CUU, CHA, OSC 8 and OSC 133/633;E: every cell's character, wide characters, attributes and underline styles, 16/256/true colors, blank cells with a background, soft wraps, the cursor, hyperlinks (with `CUI_VT_FEATURE_LINKS`) and command marks with their exit codes, command lines and run times (with `CUI_VT_FEATURE_MARKS`; a command still running is saved as ended). Pictures, the title, modes and the alternate screen are not kept. `cui_vt_load` checks the header and the length and refuses any byte or sequence outside that set (so a file from elsewhere can never make the screen answer, ring, set a title or ask for the clipboard), then writes the stream as output: a screen of the same size comes back cell for cell, another width wraps the rows again. The format is documented in `cui.h`; compression is the app's. 5000 rows of 120 coloured columns save in about 2.8 ms and load in about 2 ms (Release, `-Os`), 75 bytes a row before compression. Nothing changes for screens that are never saved (`cui_test_vt_save` checks exact cells, wide characters, colours, the cap, links, marks, the alternate screen, another width, and cut-off, newer, damaged and hostile files).

- **Terminal screen: command marks, progress and copy requests (opt in): `CUI_VT_FEATURE_MARKS`, `cui_vt_mark`, `cui_vt_mark_count`, `cui_vt_mark_get`, `cui_vt_mark_at_row`, `cui_vt_mark_near`, `cui_vt_mark_command`, `cui_vt_mark_output`, `cui_vt_mark_seq`, `cui_vt_mark_select`, `cui_vt_mark_selected`, `cui_vt_now_ms`, `cui_vt_progress`, `cui_vt_take_clipboard`; `cui_vt_opts.marks`, `cui_vt_result.mark`.** With the feature the screen keeps a mark per command from OSC 133 (A prompt, B command, C output, D;exit end) and VS Code's 633 (with E;command line), whole or split across writes; the marks follow their rows through scrolling, scroll regions, inserted and deleted lines, a resize, REFLOW and the alternate screen, and go when their prompt row leaves the scrollback. The command's text and its output come back as text (wrapped rows joined, snprintf style). OSC 9;4 progress is kept, and OSC 52 copy requests are decoded (up to 1 MB; queries are never answered) for the app to carry out or not. A view with `.marks` draws a tick per command beside the scrollbar's thumb while it shows (red for a failed command, the accent for the selected one), a click on a tick returns its mark, and `cui_vt_mark_select` scrolls a mark into view and selects its output. A mark costs about 115 bytes; scrolling with marks costs nothing more. Without the feature OSC 133, 633, 9;4 and 52 are skipped as before and nothing is kept; without `.marks` the view draws as before and `mark` is -1 (`cui_test_vt_marks` checks).
- **Terminal screen: a look per view (opt in): `cui_vt_opts.look` (`cui_vt_look`) and `cui_vt_cursor_request`.** An app can give each terminal view its own color scheme (the 16 colors, text, background, cursor, the character under a block cursor, the selection), padding (used as given, 0 is none) and cursor (a shape and blinking), read every frame, so a change shows at the next one. A program that asks for a cursor style (CSI Ps SP q) wins while it runs, and Ps 0 or a reset hands it back; blinking (530 ms on, 530 off) runs only while the view has the keyboard and the window the focus, and a key or output shows the cursor again. Without `.look` every view draws the same pixels as before and never blinks (`cui_test_vt` checks); `cui_vt_cursor_shape` is unchanged.
- **`cui_font_load_system(ui, family)`** loads an installed font by family name ("Consolas", "Cascadia Mono"): Windows finds it in the Fonts keys of HKLM and HKCU (read only) and maps the file instead of copying it (a collection at the face named), with GDI's copy of a single font file as the last resort; -1 when it is not installed, and elsewhere. **`cui_font_get_role(ui, role)`** gives the font a role uses now, so a role that was replaced can be put back. Opt in: nothing is loaded unless asked (`cui_test_sysfont` checks Consolas costs under 400 KB of private memory).
- **`cui_doc_tab.tint`**: a wash of a colour over a document tab (16 % selected, 12 % otherwise) and a 2 point line of it along the tab's top, for a tab that needs to stand out (an elevated shell). Zero draws exactly as before (`cui_tests` checks).
- **Terminal screen: find in the scrollback (opt in): `cui_vt_find`, `cui_vt_find_get`, `cui_vt_find_match`, `cui_vt_find_step`, `cui_vt_find_select`, `cui_vt_find_clear`, `cui_vt_opts.find`, `cui_vt_result.scrolled`.** Searches the scrollback and the screen (only the screen under the alternate one) for plain text or a regular expression (`CUI_FIND_CASE`, `CUI_FIND_WORD`, `CUI_FIND_REGEX`); a wrapped line is one line, so a match may go on into the next row, and wide characters count as their two cells. Without `CUI_FIND_CASE` ASCII, Latin-1, Greek and Cyrillic letters match either case (a regular expression: ASCII). Matches are (row, column, length in cells), oldest first, at most 50000; a new search starts at the newest, a search again keeps the current match on the same text. A view with `.find` marks every match on screen (the code editor's find look; the current one in the warning colour), scrolls the current one into view and selects it whenever it moves, so Ctrl+C copies it, and finds the query again at most every 100 ms while output arrives. 5040 lines of about 80 columns: plain 0.9 ms, `err(or)?` 1.1 ms, `\b[a-z]{9}\b` 4.8 ms (Release, i5-8350U). Nothing changes without a search: no memory, the same pixels (`cui_test_vt_find` checks).
- **`cui_focus_select_all(ui, id)`** gives a text field the keyboard with its text selected (a find bar opened again), and **`cui_get_platform(ui, out)`** reads the platform services back, to wrap one (a test that keeps the clipboard to itself).
- `cui_regex_search` skips the positions where no match can start (the first bytes a pattern can match are worked out when it compiles); the results are the same, found faster.
- **Terminal screen: the program's folder and its bell: `cui_vt_cwd`, `cui_vt_cwd_host`, `cui_vt_bell_count`.** OSC 7 (`ESC ] 7 ; file://host/path ST`, which shells send at each prompt) is read and percent-decoded; `cui_vt_cwd` gives the folder ("C:\Users\me" for `file://pc/C:/Users/me`, a drive path with backslashes; "/home/me" stays as it is), or NULL when none came or the last one named another machine (the host counts as this one when it is empty, `localhost` or the machine's name); `cui_vt_cwd_host` gives the host as sent. A BEL outside a sequence is counted, never shown or played: compare `cui_vt_bell_count` with the count you saw last and ring your own way (the BEL that ends an OSC is no bell). Nothing changes for apps that do not ask; the OSC buffer holds 2048 bytes (was 160) so a long folder fits.
- **Terminal screen: a resize reflows the wrapped lines, in the scrollback too (opt in): `CUI_VT_FEATURE_REFLOW`, `cui_vt_resize_sent`, `cui_vt_reflows`.** A new width joins the rows the right edge wrapped (soft wraps, not line ends) and wraps them again, as Windows Terminal does: attributes go with their cells, a wide character is never split (it moves on and leaves a padding cell that a later reflow drops), the cursor keeps its place in its line, spaces at a line's end go. The main screen is laid out as a Windows console host lays out its own buffer (its first row starts a line, rows that no longer fit go into the scrollback with the cursor kept on screen, a wider screen keeps its top row), so the host's absolute cursor moves and the system host's repaint after a resize land on what is already shown. The alternate screen is cut, not reflowed; the main screen behind it is reflowed once, from how it was. Scrollback rows holding a sixel picture keep their row and picture. A view clears its selection and stays on the same text when it looks back. `cui_vt_resize_sent` (call it when the program behind hears of the size) makes a drag reflow from what the host last heard, so rows pushed out at a narrow width come back. 5000 lines of scrollback at 200 columns reflow in about 0.6 ms (Release). Without the feature a resize cuts exactly as before.
- **Terminal screen links (opt in): `CUI_VT_FEATURE_LINKS`, `cui_vt_opts.links`, `cui_vt_result.link`, `cui_vt_link`, `cui_vt_link_find`, `cui_vt_hyperlink`.** The feature keeps OSC 8 hyperlinks with their cells: a 16-bit id per cell into a table of URIs, allocated at the first link, the scrollback keeping ids only for lines that hold one; without it OSC 8 is skipped as before. `.links`: while Ctrl is held the link under the mouse is underlined and the pointer is a hand, and a Ctrl+click returns it in `link` (a URL, or a path with its line and column) instead of starting a selection. A link is an OSC 8 one (dotted underline) or text: http, https and file URLs (trailing punctuation and brackets they did not open left out), Windows paths (absolute, relative, UNC, quoted with spaces) and the positions compilers, git and shells print (`path:line:col`, `path(line,col)`, Python's and PowerShell's forms). Detection runs only while Ctrl is held, and only when the cell, Ctrl or the text changed (about 2 us a line).
- **Terminal screen selection (opt in): `cui_vt_opts.smart_select`, `cui_vt_opts.copy_on_select`.** `.smart_select`: a double click takes a whole path or URL (else the word) across wrapped rows, a triple click the whole wrapped line, and copies lose the spaces at their line ends. `.copy_on_select` copies a selection as soon as it is made; a right click then always pastes.
- **Terminal screen: copy and paste are the app's (opt in): `cui_vt_opts.no_clipboard_keys`, `cui_vt_opts.copy`, `cui_vt_opts.paste`, `cui_vt_result.selected`.** With `.no_clipboard_keys` the view neither copies nor pastes on Ctrl+C, Ctrl+Shift+C, Ctrl+V and Ctrl+Shift+V (Cmd+C, Cmd+V): they reach the program like any other key unless the app takes them first with `cui_key_consume`, so an app can rebind them. `.copy` copies the selection in that frame as Ctrl+Shift+C did (`copied` says whether there was one), `.paste` pastes as Ctrl+V did (the text in `paste`), and `selected` says whether a selection is shown, so Ctrl+C can copy only then. A right click still copies or pastes. Without the option nothing changes.

- **A true black dark theme (opt in): `cui_set_dark_style`, `cui_get_dark_style`, `CUI_DARK_BLACK`; `cui_ctx_desc.dark_style`, `cui_app_desc.dark_style`, `CUI_DARK=black`.** The dark theme keeps its layered grays by default (`CUI_DARK_GRAY`). The black style puts the canvas, side bars, activity bar and tab strips on #000000, cards, inputs, popovers, menus and dialogs on #111111, and tells layers apart by hairline borders (white at 8%, subtle 5%, strong 20%) rather than gray fills; text is #F5F5F5, #A3A3A3 and #8F8F8F, hover white 8%, pressed 11%, status #34D399, #FBBF24, #F87171 and #60A5FA, tooltips a near-black bubble with a hairline, and docked panels and their selected tabs sit on the black canvas. With `CUI_ACCENT_BLUE` the accent is one cobalt, #3D63F0, with white on it. It animates like `cui_set_theme`; the light theme is the same in both styles. `cui_component_shots --black` (or `--black-blue`) renders every component in it.
- **Activity bar: groups, a More menu when the bar is short, and tooltips beside the bar: `cui_activity_item.group`, `cui_activity_bar_opts.fold`.** `.group` puts a short hairline above an item. With `.fold` the bar never grows taller than the space it has: the last top items that do not fit go into a More button whose menu lists them by name, and it carries the selection mark while the selected item is folded. Fix: an item's tooltip showed above it and covered the icon over it; it now shows beside the bar (to the right of a bar on the left edge).
- **Document tabs and docking: a menu of every tab when they do not fit (opt in): `cui_doc_tabs_opts.overflow_menu`, `cui_dockspace_opts.tab_menu`.** While the tabs overflow the strip, a chevron at its end lists them all, the selected one checked; choosing one selects it and scrolls it into view.
- **Nav items: a row height of their own (opt in): `cui_nav_opts.height`.** 0 keeps 32 points.
- **A short press with no bounce (opt in): `cui_theme.press_time`.** Buttons, chips and tiles scale to 0.97 and back in this many seconds, eased with no overshoot; 0 keeps the springy press.
- **Windows: a first window that fits the screen (opt in): `cui_app_desc.fit_work_area`.** A window opened at a size (no saved placement) larger than the work area of its monitor is made smaller to fit, never below its minimum size, and centred: 1200 x 780 on a 1366 x 768 screen at 125% opens at about 1093 x 545.
- **Chat composer: focus from the app and whether it has the keyboard (opt in): `cui_composer_opts.focus`, `focused`; the `[` and `]` keys: `CUI_KEY_LEFT_BRACKET`, `CUI_KEY_RIGHT_BRACKET`.** `.focus` gives the composer's text the keyboard that frame with the caret after its last character, for an app that opens a thread ready to type or puts text in itself (a recalled prompt, a completion); `.focused` reports whether the text has the keyboard, so the app can take the arrows, Tab or Enter for a menu of its own before the composer reads them (`cui_key_consume`). With a caret that stops blinking (`cui_set_caret_blink` > 0, `follow_system_caret`) the focus given this way shows the caret steady at once, so a window that opens ready to type draws nothing at rest; typing or moving the caret makes it blink as usual. The bracket keys come from every backend (Windows VK_OEM_4 and VK_OEM_6), have names in `cui_key_name`, and go out as their own key records in the VT view's Windows key mode; for shortcuts such as Ctrl+Shift+[ and ]. Unset, the composer behaves as before. New tests in `tests/test_main.c` (focus, the caret at the end, focus going away, no frame for a steady caret) and `tests/test_vt_keys.c`.

- **Node editor: a state color and a badge on a card, and selection from code (opt in): `cui_node_opts.accent`, `badge`, `badge_tone`; `cui_node_select`.** `.accent` (a color or a token such as `CUI_COLOR_SUCCESS`) tints a card's title row and draws a stripe down its left edge, for a node's state in a run (running, waiting, done, failed); `.badge` puts a small pill with that word at the right of the title, in `.badge_tone`, the title cut before it. `cui_node_select(ui, node_id, focus)` selects one node from code (one the app just added, one picked from a list) and with `focus` gives its card the keyboard, so the arrows, Delete and Tab go on from there. Unset, cards look and behave as before. New test in `tests/test_main.c` (both options and themes, selection with and without focus, the arrows after it, a click after it).
- **The standard edit menu: `cui_edit_items`, `cui_edit_command`, `cui_input_use_edit_menu`, `cui_code_editor_opts.edit_menu` (all opt in).** `cui_edit_items` puts Undo, Redo, Cut, Copy, Paste, Delete and Select all into any menu, each disabled when it can't act on the text input, text area, code editor or markdown view that was right-clicked (read only, no selection, nothing to undo; Paste is on whenever the text is editable, the clipboard is not read), and performs the one chosen through that widget's own undo and clipboard code (a paste is one undo step). `cui_edit_command` does the same from code, so apps no longer type fake Ctrl keys into a widget. `cui_input_use_edit_menu(ui, true)` makes every text field open the menu on a right click, the caret moved to the click unless it is in the selection; a code editor does with `.edit_menu`. Options: `copy_only` for a read-only view, `hide_undo`, `hide_select_all`, `keys` (rebound shortcuts), `no_perform`. Off, nothing changes.
- **Fix: text document undo after an undo.** A merged edit (an editor's typing on) made right after an undo joined the step before the undone ones, so one undo took both away; it is a step of its own now, as every other edit after an undo. `cui_text_doc_set_history` with fewer steps while every step was undone dropped the oldest steps the text did not have, which left the history pointing before its start (wrong text on redo, or a crash); it drops the redo steps farthest away instead. The intermittent `test_undo` failure in `tests/test_textdoc.c` was the test's own: its history walk could end before step 10. New `test_undo_seeds`: 240 seeds of random edits (replace, merged, parts, prepared and shared prepared texts, bytes documents), undo, redo, `set_history`, `clear_history` and `set` against a model of the history, under 2 s; the tests run in file order again.
- **Schedule picker: the minutes field is wide enough for its value and suffix.** Every N minutes showed "min..." because the number box kept its 132 pt width with the suffix; it is 168 pt now.
- **Code editor: typing in the find bar never holds a frame on a big document.** On a document longer than 1 MB the find bar searches about 1 MB from the caret in the frame (a quarter of that for a pattern); when no match is there, the rest of the search (forward to the end, then from the top, or backward) runs on another thread over a snapshot and its match is selected when it is done, if the query and the selection are still the ones it began with. An edit meanwhile searches again over the new text; a new query, a moved selection or closing the bar drops it, and `working` is true while it runs. Typing a query with no match in 100 MB: the worst frame 56 to 100 ms before, under 1.5 ms now (`cui_bench_editor --find-type`).
- **Log console over the app's own lines: `cui_log_init_source`, `cui_log_source_push`, `cui_log_source_pop`, `cui_log_source_shift`.** A `cui_log_buffer` made with a callback holds no lines or text: it counts them, and the view asks the callback for each line it draws, searches or copies (its bytes where the app keeps them, not terminated; control characters show, match and copy as spaces). An app showing a file it already has in memory no longer copies it: jneditor's Log view of a 100 MB log peaks at 144 MB instead of 272. Level filters, search, follow, selection, copy and Clear work as before; `cui_log_get` returns NULL and the appends do nothing on such a buffer. Two new fields at the end of `cui_log_buffer`; a buffer made by `cui_log_init` is unchanged. New checks in `tests/test_main.c` (`test_log_source`), `cui_bench_log --source` (1.1 million lines: a filter's frames 1.2 ms at most, as with a buffer of its own). See [Log console](docs/components-more.md#log-console).

- **`cui_text_prepare_adopt`: a prepared text over bytes the caller shares.** As `cui_text_prepare`, but the bytes are kept as they are (carriage returns too, as `cui_text_doc_adopt` keeps them) and never freed: a document that takes it (`cui_text_doc_replace_prepared`, `cui_code_editor_edit_prepared`) reads them where they lie and calls the caller's `release(text, user)` once it and its snapshots let go; a text under 64 KB is copied and released at once, and every path that drops it unused releases it too. So an app can keep one copy of a big new text for both the document and its own index of it (jneditor's Table view after a column edit: one 100 MB copy less). Existing callers are unchanged; a removal made with an empty prepared text no longer leaks its buffer. Checks added to `tests/test_textdoc.c` (in place, through undo, redo and a snapshot that outlives the document; small, unused, refused and empty texts) and `tests/test_editor_jobs.c` (documents and buffers).
- **Hex view as an editor over any byte source (opt in): `cui_hex_view_opts.read`, `on_edit`, `user`, `fixed_size`, `insert`; `cui_hex_view_focused`, `cui_hex_view_focus`; `cui_text_doc_adopt_bytes`; `CUI_KEY_INSERT`.** With `.read` the view reads only the rows in view (and what it copies) through a callback, so the data need not be in one piece; with `.on_edit` it becomes a hex editor whose every change (overwrite, insert, delete) goes to the callback: hex digits in the hex column, text in the text column (Tab switches), insert mode (the Insert key), Delete, Backspace, Ctrl+X, Ctrl+V (hex digit lists or text) and a cursor after the last byte to append; the low digit of a byte is marked `merge`, so an app keeps one undo step a byte. `cui_text_doc_adopt_bytes` is a piece table for bytes that keeps no line index. The Insert key is reported on Windows, X11, SDL2 and GLFW, and a terminal view sends it as ESC [2~.
- **What a frame's components will read, for apps that record or filter input: `cui_key_presses`, `cui_typed_text`, `cui_typed_text_consume`.** `cui_key_presses` counts a key's presses this frame (with key repeat), `cui_typed_text` gives the text typed this frame, and `cui_typed_text_consume` takes it away as `cui_key_consume` does for a key. A keyboard macro recorder reads them before the code editor runs; nothing changes for apps that do not call them.
- **Code editor: multiple cursors and column selection (`cui_code_editor_opts.multi_cursor`).** Alt+click adds a caret, Ctrl+Alt+Up and Down add one above or below, Ctrl+D selects the word and then adds the next match, Ctrl+Shift+L selects every match (at most 10 000), Alt+Shift+drag and Alt+Shift+arrows select a column (tabs to their stops, a character of any width one column, short lines left out), Esc goes back to one caret. Typing, Backspace, Delete, Enter (indentation and markdown lists), Tab, Shift+Tab, the arrows, Home, End, word moves, cut, copy and paste (one line per caret when the counts match) work at every caret, each key one undo step, with the carets back on undo; selections that meet become one. New: `cui_code_editor_add_selection`, `cui_code_editor_selections`, the result's `cursor_count`, and eight `CUI_EDK_*` commands for `.keys`. Off by default: nothing changes for editors without it. Tests in `tests/test_editor_multi.c` (buffer and document, overlapping, undo, paste, columns over short lines, tabs and UTF-8, the caps); `cui_bench_editor --multi`: 100 carets on a 10 MB document type in 0.2 ms a frame. See [Multiple cursors and column selection](docs/components-more.md#multiple-cursors-and-column-selection).

- **Code editor: folding and a minimap (both opt in).** `.folding` puts fold markers in a lane at the right of the gutter for every block (by indentation; in markdown by heading); folded lines are skipped by drawing, scrolling, wrapping and the caret, a folded line ends in a box that opens it, and a fold opens when the caret or a find match goes inside or an edit touches it. `cui_code_editor_fold` folds or opens at a line, folds every block or opens all (`CUI_FOLD_*`); the result reports `fold_count` and `hidden_lines`. `.minimap` adds a strip of `CUI_MM_WIDTH` points at the right edge with a bar a row coloured by its text and the rows in view boxed; a press or drag on it scrolls. Lines are looked at only in view (bars are kept per line and made again where edits touch), so 10 MB documents type and scroll in well under a millisecond a frame. Without them nothing changes.
- **Code editor: multiple cursors with folding.** With `.multi_cursor` and `.folding` both on, the other carets are drawn on their rows past folded lines (not on the rows of their line numbers), an Alt+click or Alt+Shift+drag below a fold picks the line shown there, a cursor or match added inside a fold (`cui_code_editor_add_selection`, Ctrl+D, Ctrl+Shift+L, undo) opens it, folding over other carets moves them out as it moves the primary one, column selection, Ctrl+Alt+Up/Down and the arrows at every caret step over folded lines, and undo or redo of an edit step on a document keeps the folds between its edits. Tests in `tests/test_editor_fold_multi.c` (wrapped and not, buffer and document, the minimap, the carets' blink and rest).
- **`cui_floating_layers`: the box as drawn this frame (`drawn`).** `cui_layer_rect` now also reports `drawn` (a popover's or menu's layout rectangle scaled about its centre and moved by its open and close animation; a full layer's is its panel), `drawn_radius` (the corners scaled the same way), `elevation` and `elevation_alpha` (its shadow), so a host that cuts a native child window (a web view) out for the box and redraws its edge can follow every frame of the animation, not only the box at rest. New fields at the end of the struct; nothing else changes. Checks added to `tests/test_floating_layers.c` (the box grows from under full size inside its rectangle, the radii scale with it, rest equals the layout). See [Reading layout results](docs/layout.md#reading-layout-results).
- **Marked text in the markdown view: `cui_markdown_opts.highlights`, `highlight_count`, `highlight_current`; the result's `highlight_y`.** Pass byte ranges of the text (ascending, not overlapping) and the view draws them under their text in the theme's warning tone, the current one (1 based) stronger, readable in light and dark. `cui_markdown_result` reports where the current one is (`highlight_found`, `highlight_y` from the top of the view, `highlight_exact`; in a big text a block not built yet is placed by an estimate, exact once it is built), so an app can scroll to it for find in page. Running text, lists, quotes, callouts and table cells are marked (also a paragraph joined from several lines); a code block only reports its line. Count 0 (the default) changes nothing: component images and gallery pages are byte for byte the same.
- **Windows, `cui_app_frames_on_change`: the system's timer message (WM_SYSTIMER) and the WM_NCACTIVATE it brings draw no frame.** With a focused text field at rest the system sends its own timer message (wParam 0xFFF8, Text Services and the system caret) to the window now and then, about 7 s after the last key on some machines, and the default window procedure answers it with a WM_NCACTIVATE to itself. Neither changes anything CUI draws (a real change of activation also sends WM_ACTIVATE, which still counts), but they counted as messages and drew one frame. ### Changed

- **One window API after merging upstream's window state.** `cui_app_set_position`, `cui_app_position` and `cui_app_desc.x`, `.y`, `.has_pos` all use the coordinates of `cui_window_placement`: the top-left corner of the window's content in desktop coordinates (pixels on Windows and X11, points on macOS). On Windows they used the outer frame's corner; with `custom_titlebar` the content is the whole window, so nothing moves there, and a window with the system frame now lands its content where it is asked. `x`, `y`, `has_pos` and `start_maximized` are folded into a placement when the window is created, so they work on every backend, a place on no monitor is left to the system, and a fixed-size window is not maximized. `cui_app_minimize` is the one function of both sides; `cui_app_toggle_maximize` and `cui_app_is_maximized` are built on `cui_app_restore`, `cui_app_maximize` and `cui_app_window_state` and so work on every backend. `cui_app_position` reads the content's corner now, and where a minimized window comes back; it returns false on Wayland. A window opened maximized from a placement keeps the quick first show on Windows (shown with its first picture) and a shortcut's minimized or maximized setting still wins.
- **The file browser's sidebar lists drives and volumes**: drive letters with their labels on Windows, mounted data volumes on Linux and browsable volumes on macOS, under their own heading below Places. It scrolls, so custom `places` are no longer cut off after six, and Reload (F5) or reopening a file picker reads the drives again. The filter field now has the height of the path bar beside it ([#96](https://github.com/yappologistic/CUI/issues/96)).
- **Scrolling with the software renderer costs half or less.** A scroll used to redraw every tile under the scrolled area. Tiles are now hashed relative to themselves, so content that moved by whole pixels is recognized, and those tiles have their pixels moved instead of drawn (up to three distances a frame); only what came into view or really changed is drawn, and every frame stays pixel for pixel what drawing it whole gives. Drawing runs on worker threads kept for the renderer's life (new threads were started for every rectangle of every frame) and each tile row looks only at the shapes over it; shadows above and below their shape are worked out once per row. On Windows only the changed rectangle is copied to the window, and a `WM_PAINT` copies the whole frame again. Scrolling a 5,000 message chat in a 1180×780 window at 150%: raster 2.1 to 1.2 ms (median), frame 3.1 to 1.8 ms, 95th percentile 4.7 to 3.2 ms; the code editor's raster 3.6 to 1.6 ms; a chat app's 5,000 item transcript 5.2 to 2.8 ms a frame (95th percentile 7.5 to 3.7). A new benchmark, `cui_bench_scroll`, measures it per phase, and with `--check` (four ctest cases) compares every incremental frame with a whole one. See [Performance](docs/performance.md#scrolling-with-the-software-renderer).
- **Windows apps show sooner and use less memory.** With the Auto renderer the first frames are drawn in software while OpenGL starts on another thread (loading the GPU driver and compiling the shaders took 150 to 200 ms before the first frame could be drawn); from the frame after it is ready OpenGL draws, and the textures made meanwhile keep their handles. The window is shown with its first frame and activated right after it, instead of being activated empty first (Windows spends 50 to 80 ms on that), and the first frame waits for no frame pacing. OpenGL gets a pixel format without the depth and stencil buffers CUI never used (7 to 14 MB for a 1080 x 720 window at 150%), the glyph atlas starts at 512 x 512 instead of 1024 x 1024 and grows as before, and the system emoji font is mapped instead of read (Segoe UI Emoji took 12 MB of the app's own memory). On an Intel laptop two apps went from about 220 to about 115 ms to their first frame (as an outside script measures it, from starting the process) and from about 76 to about 69 MB idle. `cui_app_is_software` is true until OpenGL takes over. MinGW apps built with `cui_app_target` link libgcc and winpthread in, so they no longer need `libwinpthread-1.dll` (stb_image's thread-local variables pulled it in), which Windows looked for along PATH at every start. See [Performance](docs/performance.md#starting).
- **Code editor: replacing the whole text is fast.** `cui_code_editor_edit(ui, id, 0, len, text, ...)` over a 20 MB text with 50 MB of formatted text took a 74 ms frame and then a 288 ms one in an app; the apply is now one frame of 23 to 28 ms for a log and 29 to 39 ms for a JSON of 1.7 million lines with its `{` at the caret (200 to 320 ms before, in `cui_bench_editor --replace`, i5-8350U), and Ctrl Z and Ctrl Shift Z take about 10 and 25 ms (30 to 50 and 70 to 100 before). The text you pass is kept once, as the undo step's inserted bytes (it was copied twice more), the line breaks are found with SSE2 compares while it is copied into your buffer (they were three `memchr` passes and a per byte loop), the new lines of a big edit get their wrap counts as a text that just opened does (a guess, counted when in view) instead of one walk per line, and a new `.revision` over 50 MB makes the index again in about 20 ms (was 90 to 130). Bracket matching looks for a partner within 1 MB of the bracket (an unmatched or far `{` at the start of a 50 MB text used to read to its end, 150 ms, each time the text changed). Measure with `cui_bench_editor --replace`.
- **The code editor keeps its line index between frames** and patches it, the wrap counts and the markdown and block comment line states where each edit happens, instead of making them again from the whole text every frame; lines too long for the width are counted when they come into view. Undo keeps each edit's removed and inserted bytes instead of a copy of the text, and an unmatched bracket is looked for once, not every frame. Without `.revision` the editor still notices any change to the text by a hash each frame (about 20 ms a frame for 100 MB, against 90 to 190 ms before). When the text changes outside the editor, its undo history is cleared, since it would no longer fit the text.
- **Renderers: a sixth shading mode**, `CUI_SHADE_DITHER`, for the dither components. A renderer of your own needs its few lines from the reference shader in [Rendering](docs/rendering.md) to draw them; everything else draws as before.
- **Line charts take `stacked`**: each series sits on the ones before it, and the axis covers their sum. It used to apply to bar charts only.
- **A calmer series palette.** The six chart colors keep their order (blue, orange, aqua, violet, yellow, magenta), so neighbours stay apart under color blindness, but now share one lightness and about one chroma in each mode. No series shouts over another or over the rest of the interface, and the light colors keep 4.2:1 or more on white.
- **Bar, donut and line charts** step back so the data leads: faint dashed gridlines over a solid zero line, smaller muted axis labels, slimmer bars with a small gap inside a group, and on hover a soft band behind the column with a compact chip of its values. The donut ring is thinner, its segments are parted by real gaps, and each legend row has a thin bar showing its share.
- **Heatmap and calendar heatmap** count in five steps from the empty surface up to the accent (a gray ramp under the neutral accent), so zero reads as empty and the steps read at a glance. Heatmap cells are smaller with real gaps, a Less to More key replaces the gradient scale, and hovering a cell rings it and lights its row and column labels.
- **Radial gauge** drops the needle and the tick ring for three calmer styles, with the value as the hero: a segmented arc lit in the band colors only up to the value, a clean arc with round caps, its ends labelled and a target marker, and a slim ring with a line of detail. New options: `style` (`CUI_GAUGE_AUTO` picks the segments when there are `bands`, the arc otherwise), `detail` and `color`, and a band `name` shown as a chip while the value is in that band. The default sweep is now 270 degrees.
- **Treemap and radar.** Treemap tiles are neutral, graded by size, with 3 point gaps, a label, a value and a share figure, and only the hovered or selected tile in the accent; small tiles keep a compact value. New `selected` option: a click selects a tile and a second click clears it. The radar has hairline rings, light fills under crisp outlines, points only on the series you point at (the last one otherwise) with a chip of the hovered value, and ring values kept off the lines.
- **Sankey** nodes are slim (6 points) and colored by meaning, with the new `node_colors` option and the palette or neutral gray for the rest. ### Changed

- **`CUI_TEXT_LEFT` is now 3** (`CUI_TEXT_START` is 0 and means left in a left-to-right box, so the default look is the same). Code that uses the names only needs a rebuild; code that stores alignments as numbers changes meaning. `cui_ctx_desc`, `cui_box` and `cui_text_opts` gained a `direction` field.
- **Animation runs at the display's rate.** An animating window used to draw as fast as it could whenever the swap did not wait for the display: under software OpenGL or with vsync forced off by a driver, an always-animating app drew 150 frames a second on three cores, and the software renderer was capped at 120. Frames now come at the display's refresh rate (asked from the system, 60 when it cannot tell). OpenGL notices a swap that does not wait and paces by the clock, and pointer events no longer start frames early. A mixer panel on the software renderer went from 68 frames a second at 10.6% of a core to a steady 60 at 6.8%. On Windows, timed waits use a high-resolution timer, and a raw-input flag that Wine leaves set no longer wakes every wait.
- **Dialogs, sheets and soft shadows paint about twice as fast in software.** A dialog or sheet animating over a dimmed window repaints the whole window each frame, and most of that went into its shadow and the dim layer. The inside of a shadow, where it is a flat color, is now drawn as one run; long runs of one translucent color use a per-channel table that gives the same bytes; the shadow falloff comes from a table instead of `erf` for every pixel; and the blend is inlined. The Mail example's worst frame went from 318 ms to 60 ms (one thread at 2560 × 1600), and the Assistant's sheet from 93 ms to 61 ms. Screenshots are unchanged except for 123 shadow pixels that moved by one level out of 255.
- **Smaller builds.** MinGW's linker keeps whole files (it cannot drop a function with an unwind record), so release builds of CUI now also carry link-time optimization data and the examples link with `-flto=auto`: `assistant.exe` went from 740 KB to 420 KB and `hello.exe` from 418 KB to 300 KB. Apps that do not use LTO link as before. Release builds on Linux and BSD leave out unwind tables, 6 to 7% of an app (`hello` 254 KB to 242 KB); `-DCUI_KEEP_UNWIND_TABLES=ON` keeps them.
- **Smaller Windows builds.** The core called into the emoji code to release its texture, and Windows linkers keep a whole file once anything in it is used, so every Windows app carried the emoji picker and the PNG decoder. The core now reaches emoji through a hook set when they are first used: `hello.exe` went from 478 KB to 407 KB.
- **No GPU, no OpenGL.** When the OpenGL driver draws on the CPU (Mesa llvmpipe, SwiftShader and the like, common in virtual machines and remote sessions), X11 and Win32 apps on the Auto renderer use CUI's software renderer instead, which redraws only what changed. Notes under llvmpipe went from 27% of a core to 4%. `cui_gl_is_software` tells, and `CUI_RENDERER=opengl` keeps OpenGL.
- **Full software repaints are about twice as fast.** An opaque solid, or the inside of an opaque rounded rectangle, is filled as one run of a color instead of pixel by pixel, which was most of the work on a typical screen of panels and cards. The output is identical, byte for byte, on every screenshot.
- **Per-frame buffers shrink again.** Vertices, indices, draw commands, nodes and the frame arena shrink once they have been more than four times bigger than needed for 600 frames, so a heavy page no longer leaves its buffers behind.
- **Long lists keep less state.** Scrolling through thousands of rows used to leave three state entries per row for five seconds, and the table never shrank: paging through a 5,000 row grid held 15,000 entries. Now an entry that holds only last frame's rectangle expires after 30 frames, hover fades take state only once a row is hovered, buttons and links keep none until touched, and the table packs itself when mostly empty. The same paging holds about 1,700 live entries, and 150 at rest.
- **Emoji cost less.** The emoji texture is released once no emoji has been drawn for 600 frames, which frees 1 to 4 MB after the picker closes. Small emoji use a quarter of the texture. Bitmap emoji are scaled with precomputed weights, which makes drawing new ones about three times faster, and at most 12 are drawn per frame, so scrolling the picker stays near 2 ms a frame.
- **The software renderer draws only what changed.** `cui_sw_set_incremental` keeps the last frame in the buffer and repaints only the 64 pixel tiles whose triangles changed, so a hover or a caret blink costs a few tiles rather than the window. New glyphs and emoji arriving in a texture redraw only what samples them. A frame where nothing changed draws nothing, and `cui_sw_last_damage` tells the backend which part to copy to the screen. The app's software path and the browser build use it: with the same input, the Mail example used 3.9% of a core instead of 12.9%. Output is identical to a full repaint (tested frame by frame).
- **The glyph atlas shrinks again.** It still grows when it fills up, but glyphs not drawn for five seconds (sizes from before a zoom or a change of display scale) are dropped, and the rest move into the smallest atlas they fit. A long session no longer keeps a 2048 or 4096 pixel atlas it no longer needs.
- Truncated right-to-left text puts its ellipsis on the left, where the text ends (with text shaping).
- Text field placeholders are shaped like other labels, so Arabic and other joined scripts read correctly in them (with text shaping). The text being edited stays unshaped, as before.
- **Every component page fits a phone.** Layouts that used to need more than a phone's width now rearrange instead of shrinking the preview. The calendar, countdown, radar chart, activity rings and donut legend scale down. The waffle legend moves under its grid, and the banner puts its action under the message. - **Segmented controls and button groups** tighten their padding before a label truncates.
